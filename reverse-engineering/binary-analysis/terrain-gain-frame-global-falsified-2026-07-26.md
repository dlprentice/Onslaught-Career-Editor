# Terrain gain — frame-global falsified, and the root-map oracle is circular

> Two verdicts, both negative, both measured.
>
> 1. **The frame-global hypothesis is dead.** Retail renders a non-terrain,
>    mid-range, strongly chromatic textured surface — the Kempy cube-25 sky — at
>    a per-channel gain of **exactly 1.00**, in the same frame, through the same
>    device, back buffer and presentation path as the terrain. Device gamma,
>    back-buffer format, RGB565 quantisation and the presentation path cannot
>    produce the terrain's (1.400, 1.295, 1.075).
> 2. **The compositor's byte oracle is circular.** The pinned
>    `level100-root-terrain.rgb565.bin` is generated by this project's own
>    Python transcription of the blit, gated by a hash of that Python's own
>    output. "`RenderTile` reproduces the root map byte-for-byte" proves C#
>    equals Python. It establishes nothing about retail's runtime macro cache.
>
> No gain, offset or tint was applied anywhere. No rebuild source file was
> modified. `BEA.exe` was read only; the Ghidra database was not opened.

Specimen for every byte claim: `local-lab/safe-copy-bea-pristine/BEA.exe`,
SHA-256 `e1436ef7e0ad9ccbddd43aaaca952f6e84d4b1a282835cead745efcfc32fadf4`,
2,506,752 bytes. Image base `0x00400000`, `.text` VA `0x00401000` at file
offset `0x1000`.

## 1. Frame-global: falsified against the sky at gain 1.00

### Method

`tools/sky_source_gain_probe.py` inflates the five shipped
`Assets/Level100/Sky/cube25-*.texture.aya` faces, decodes their DXT1 payloads to
RGB888 (**16,503 distinct texel colours**), and then — with no UV mapping, no
camera model and no assumption about which face is visible — scans a candidate
gain `g`, divides each rendered sky pixel by `g`, and measures the mean
Euclidean distance to the nearest shipped texel colour. A pass-through path
minimises at `g = 1`; a gain-`G` path minimises at `g = G`.

Window: `x 340…620, y 30…100` — 19,600 pixels, above the horizon ridge, right of
the cockpit frame, clear of the HUD. Frame: `level100-t025065ms.png`, the same
deterministic offset at which the terrain transfer function was measured.

### Result

| frame | window mean | argmin uniform `g` | distance at argmin | distance at terrain gain |
| --- | --- | ---: | ---: | ---: |
| retail `hud-timeline-run1/level100-t025065ms.png` | (210.23, 163.64, 104.58) | **1.00** | 1.600 | 4.634 |
| reconstruction `20260726-…-water-fixed/level100-t025065ms.png` | (195.13, 146.68, 91.52) | **1.00** | 1.113 | 3.708 |

Per-channel scans (each channel swept 0.90…1.46 with the other two pinned at
1.0) put **R, G and B each at exactly 1.00** on both frames. The uniform scan is
sharply peaked — retail's distance rises monotonically to 9.205 at `g = 0.90`
and 3.847 at `g = 1.12`.

The reconstruction is the calibration control, not a second unknown: its sky
shader is `ALBEDO = texture(sky_texture, UV).rgb`, `unshaded`, with no gain
constant (`rebuild/OnslaughtRebuild.Godot/Level100SkyAsset.cs`). It measures
1.00, so 1.00 is what a pass-through path scores. Retail scores the same.

### The same result without any fitting

21.73% of retail's sky-window pixels are **exact** members of the shipped texel
set; after dividing by the terrain gain only 2.40% are. The window's most common
colours are shipped texels verbatim and at mid range:

| retail on-screen colour | pixels | in shipped palette |
| --- | ---: | --- |
| (198, 150, 90) | 98 | yes |
| (148, 113, 74) | 73 | yes |
| (198, 158, 99) | 71 | yes |
| (214, 170, 107) | 63 | yes |
| (222, 174, 123) | 60 | yes |

Over the whole `y 0…100` sky band, retail's single most common non-white colour
is **(181, 138, 132)** at 212 px — which is texel-exact: it occurs 1,133 times
in `cube25-cent` and 850 times in `cube25-left`. Under the terrain gain that
texel would render as (253, 179, 142).

### Why this is decisive where the earlier flat-band anchor was not

`local-lab/WATER-SKY-EVIDENCE-2026-07-25.md` already recorded the flat texel
(252, 249, 255) rendering as (252, 250, 255). That bounds the gain only in the
highlights, where any gain above ~1.012 clips — it cannot exclude a curve that
is 1.36 at mid tone and 1.00 near white. The present measurement is at
mid-to-upper-mid range with a strong hue (R/B ≈ 1.6) and finds gain 1.00 in
every channel independently, so no monotone per-channel transfer function of any
shape survives.

Independently, commit `93b514c0` measured the terrain gain **flat across macro
luminance** (1.38, 1.38, 1.34, 1.35 across bins), which is a linear gain, not a
gamma; and the three per-channel gains differ (1.400 / 1.295 / 1.075) at
overlapping input ranges, which no single value-dependent frame transform can
produce.

**Verdict: frame-global is eliminated. The mechanism is terrain-specific.**

## 2. The pinned root map is not retail-derived

`rebuild/tools/materialize_retail_assets.py:3292` `_render_root_terrain` is a
Python implementation of the blit: it parses `MAPT`/`MCEL`/`MSHD`/palettes,
rebuilds the lighting gradient from the `HFLD` sun and ambient, runs the same
7-step material blend and `shade >>= static_shadow` rule, applies pine shadows,
and packs RGB565. Its output is written to
`Assets/Level100/Source/level100-root-terrain.rgb565.bin` and gated at line 3450
against `ROOT_TERRAIN_TEXTURE_SHA256`, whose in-source comment states plainly:

> "Exact initial root texture produced by the released compositor **reconstructed
> below**. The materializer refuses to publish if those pixels do not reproduce."

The constant is a hash of that Python function's own output. No retail runtime
cache was ever read, dumped or compared.

`rebuild/OnslaughtRebuild.Client.Tests/Level100TerrainCompositorTests.cs` then
asserts that the C# `Level100TerrainCompositor.RenderTile` reproduces that file
byte-for-byte, and its own summary calls the file "a byte oracle for the
compositor itself".

**So the check is C# ≡ Python.** Both sides are this project's single reading of
the shipped bytes. The check is a genuine and useful cross-implementation
regression gate, and it should be kept — but it is **not** evidence that the
reconstruction's macro cache equals retail's runtime macro cache, and it must
not be cited as such. The measured "retail / macro = 1.400, 1.295, 1.075" is a
ratio against an *unvalidated* denominator.

One concrete divergence the oracle cannot catch, visible in the two sources:
`terrain-shade-plane-origin-2026-07-26.md` §3 records that the blit samples the
**2×2 shade corners and bilinearly interpolates them in 8.8 fixed point** across
each 8×8 cell, while `_render_root_terrain` takes the single corner
`shade[min(y+1,511)*512 + min(x+1,511)]`. That is consistent with retail's
per-pixel terrain standard deviation of 0.40/0.37/0.31 against the
reconstruction's 0.048/0.062/0.057 (commit `7b53a174`). It does not by itself
raise the mean.

## 3. Also eliminated this pass, by bytes

### 3.1 There is no second gradient doubling, and no second gradient build

Scanning the pristine specimen for every `E8 rel32` whose computed target is one
of the three terrain-lighting entry points:

| target | function | `E8` call sites in the whole image |
| --- | --- | --- |
| `0x0047e8e0` | `CHeightField__InitColorGradient` | **1** — `0x0047f7ea` |
| `0x0047f750` | `CHeightField__Load` | **1** — `0x004910d6` |
| `0x0047eff0` | `CLandscapeTexture__BlitTileRegionWithLightingMask` | 3 — `0x0048eb5e`, `0x0048ecee`, `0x0048f01d` |

`CHeightField__InitColorGradient` is called only from inside
`CHeightField__Load`, and the in-place doubling/clamp loop is the tail of that
same `CHeightField__Load`. One build, one doubling, per level load. A second
doubling would have moved the gradient's saturation point from shade 29 down to
shade ~14 — below the island's mean of 22 — and would have reproduced the
measured deficit almost exactly. **It does not exist.**

Corroborating the loop bound: the doubling runs
`for (p = this+0x10d0; p < this+0x13dc; p += 3)`, i.e. **65** iterations over a
64-entry table. The 65th touches `this+0x13d0…0x13d8`, the fog-colour triplet
`InitColorGradient` copies from `+0x13c4`. Fog is already exhaustively
eliminated (commit `93b514c0`), so this is noted, not pursued.

### 3.2 The sun colour rewrite in `CHeightField__Load` is a no-op

`CHeightField__Load` writes `this+0x107c` (the sun colour) *after* calling
`InitColorGradient`, so the gradient is built from the as-authored chunk bytes —
the materializer reads the right field. The rewrite is in any case identity for
Level 100: with sun `0xBDB179` and ambient `0x0D0F2B` it computes
per-channel `sun+ambient` = (202, 192, 164), finds the max ≤ 255 so skips the
rescale, then stores `((amb_R*0xffff + 202) << 16) | ((192-15) << 8) | (164-43)
| 0xff000000`. The red term truncates to 189 in the low 16 bits, so the stored
value is `0xFFBDB179` — the original with alpha forced to `0xFF`.

## 4. What is left

With frame-global now eliminated by measurement, and with the compositor's only
retail-side validation shown to be circular, the surviving candidate is the one
the circular check was masking: **the reconstruction's macro cache is not
retail's macro cache, and the 1.36× lives in that difference.**

That is the same place commit `6c905b09` landed from the other direction —
retail's terrain renders as if the lighting index were at the gradient's
saturation point (saturated / as-authored = 1.348, 1.306, 1.023 against the
measured 1.360, 1.285, 1.073) while the authored plane averages 22 of 63. The
plane is proven to be verbatim asset data with no writer, and the gradient is
now proven to be built and doubled exactly once. So the unexplained step is
**how `0x0047eff0` turns a shade byte into a gradient entry** — the bilinear 8.8
index expression, the `5`/`0`/`0`/`8` trailing arguments the three call sites
pass, and the mip parameter — which is precisely the part of the chain whose
reimplementation has only ever been checked against itself.

The next measurement must break the circularity directly: obtain retail's
runtime macro cache content rather than reasoning about the producer. Nothing
below that standard should be treated as closing this.
